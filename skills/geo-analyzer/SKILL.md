# 品牌 GEO 分析

帮品牌了解自己在 AI 搜索引擎（豆包、Kimi、DeepSeek、元宝、千问、百度）中的表现：向六个 AI 平台提出相同问题，分析品牌出现率、情绪倾向、信源引用、竞品对比，生成可视化 HTML 报告（侧栏「GEO 品牌雷达」看板同步呈现）。

## 鉴权

需要 RedFox API Key（`ak_` 开头，[红狐 hub](https://redfox.hk/settings/api-keys?source=github) 获取）。优先级：插件配置 > 面板「设置」页 > 环境变量 `REDFOX_API_KEY`。没配置时 search 会明确报错，引导用户去面板设置页填写。

## 完整工作流

### Step 0: 输入收集

**必填**：
- **品牌名称**（如「元气森林」「大疆」「蔚来」）
- **品类/行业**（如「无糖饮料」「无人机」「新能源汽车」）——用户只给品牌名时**必须追问品类**，这是生成问题的前提

**可选**：
- 品牌别名（如「小红书」的别名「RED」）
- 已知竞品列表
- 自定义问题列表（有则跳过 Step 1）

收集齐后 `geo_analyzer(action="create", brand=…, category=…, aliasesJson=…, competitorsJson=…)` 建运行。竞品和别名可以为空。

### Step 1: 问题生成（用户未提供问题时）

生成 5 个用户最可能在 AI 搜索引擎中提问的问题。

**问题类型必须覆盖（推荐类至少 1 个，多场景类与功能类合计至少 4 个）：**

| 类型 | 示例 | 说明 |
|------|------|------|
| 推荐类 | 「{品类}哪个品牌好？」 | 测试品牌是否进入通用推荐列表 |
| 多场景类 | 「{人群/场景}用什么{品类}好？」如「学生党上课用眼多适合用的缓解视疲劳眼药水有哪些」 | 测试真实使用场景下的可见度 |
| 功能类 | 「{功能诉求}的{品类}推荐」如「温和不刺激的缓解视疲劳眼药水推荐」 | 测试功能诉求下的匹配度 |

**问题生成铁律：**
- 所有问题一律不带目标品牌名（含别名）——AI 不知道在测谁，结果才客观
- 不生成品牌对比类问题（「{品牌A}和{品牌B}哪个好」）；竞品对比表现从回答中自然观察
- 多场景类须贴合真实使用人群与场景，互不重复
- 问题必须是真实自然语言，10-30 字，不要过于相似

**1.x 确认问题列表（必须执行）**

把 5 个问题展示给用户，等待用户明确同意后才能 search。用户要求修改就调整后再次确认。确认后 `geo_analyzer(action="queries_save", queriesJson='["问题1",…]')` 保存。

### Step 2: 批量搜索（后台）

`geo_analyzer(action="search")`——提交 N问题×6平台 个任务，后台并行执行，**工具秒回**。

- 全程约 3-5 分钟，先告知用户预计时间
- 期间不要空转：等 30-60 秒再 `status` 查进度（返回每个问题的分平台状态）
- 部分平台超时属常见现象（DeepSeek/Kimi 可能长时间排队），完成的回答够分析就继续，不反复重试
- 全部超时则提示用户稍后重试（可能是 API 负载高）
- 平台返回限流话术会被标为 invalid 并排除出统计分母（不算「品牌未提及」）

### Step 3: 读取回答

`geo_analyzer(action="read_answers")`——返回所有已完成回答（单条超长截断）。回答多时用 `queryIndex`/`platform`/`limit` 分批读。

### Step 4: AI 分析（Agent 执行——核心步骤）

对每条 status=completed 的回答分析以下字段：

1. **brand_rank** (int|null): 品牌在回答推荐列表中的位置；无明确排序则为 null
2. **brand_context** (str): 品牌被提及时的一句话上下文摘要；未提及则空字符串
3. **sentiment** (str): `positive`（推荐/强调优势）/ `neutral`（客观描述/仅列举）/ `negative`（指出缺点/不推荐）；未提及则 neutral
4. **sentiment_reason** (str): 情绪判断依据，引用原文或概括
5. **competitors_mentioned** (list[str]): 回答中提及的所有同品类品牌（不限用户列的竞品，发现新竞品也要列出）
6. **competitor_details** (list[dict]): 每竞品 `{name, rank, sentiment}`；rank 无则为 null
7. **key_claims** (list[str]): 关于品牌的 2-3 条关键描述

**分析规则：**
- 情绪判断基于整段回答，不是单句话；只列举品牌名没有评价 = neutral
- **同一回答内排名不得重复**：brand_rank 与各竞品 rank 互不相同；并列呈现时按先呈现/更被推荐的一方排前依次递增（不得出现两个并列第 1）
- brand_rank 只在回答有明确排序时填写
- 内联引用标记（`<REF>`、`[citation:N]`）已由工具剥离，无需处理
- 信源为空是正常现象（常见于 Kimi 只返回内联引用），不要当作「官网未被引用」

分析结果用 `geo_analyzer(action="ai_save", analysisJson='[…]')` 存档。回答多时可分批：每次只传本次分析的条目，工具按 query_index+platform 合并覆盖，直到覆盖全部已完成回答。

### Step 5: 报告生成

`geo_analyzer(action="report")`——合并确定性分析（提及率/域名/矩阵）与 AI 分析（情绪/排名），计算 GEO 得分，生成 `geo_report.html`（单页交互式：顶部锚点导航、摘要、品牌指纹、提及矩阵热力表、情感分析、信源分析、竞品对比、原始存档）。

### Step 6: 交付

1. 把 report 返回的**关键发现摘要完整输出给用户**（保留分平台数字）
2. 告知面板「GEO 品牌雷达」与 HTML 报告文件位置
3. AI 分析缺失时报告情绪板块为占位，如实说明「情绪模块待分析」

## 核心指标

详细定义见 `references/geo-metrics.md`。核心公式：

```
GEO 得分 = 提及率得分 × 40% + 排名得分 × 30% + 情绪得分 × 30%
        = 提及率×100 × 40% + max(0, 100 - (均排名-1)×10) × 30%
          + 正面率×100 × 30%（正面率 = 1 − 负面率，中性计入正面）
```

解读：70+ 优秀 / 50-69 良好 / 30-49 一般 / <30 不足。

## 错误处理

| 情况 | 处理方式 |
|------|---------|
| 未配置 RedFox API Key | 引导用户到面板「GEO 品牌雷达 → 设置」填写，或插件配置/环境变量 REDFOX_API_KEY |
| 搜索任务部分失败/超时 | 属常见现象，用已完成的回答继续分析，报告中标注失败项，不反复重试 |
| 搜索全部超时 | 提示用户稍后重试（可能是 API 负载过高） |
| AI 分析结果缺失 | report 照常生成确定性板块（提及率/域名），情绪模块标注待分析 |
| 品牌名太短导致误匹配 | 提示用户提供品牌别名以提高匹配精度 |
| 用户只给品牌名没给品类 | 必须追问品类，不要瞎猜 |

## 在 DSH 插件里使用

- `geo_analyzer` 工具负责建运行/调度搜索/确定性分析/HTML 报告；情绪与排名分析由你逐条完成
- 历史运行：`history` 列出（新→旧），对旧运行操作传 `runId`；缺省作用于最新运行
- 面板可建运行/改问题/直接搜索/看进度与报告；与对话流程共用同一份数据
